# Changelog

All notable changes to Instar are documented here. This project follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Instar is in **v0.x** — the API surface is unstable until v1.0.0. Breaking changes may land in any 0.y release; we will call them out in the corresponding `### Changed` or `### Removed` section.

## [Unreleased]

### Added

- **An absolute judge: `--criteria` on `instar arms` and `instar rejudge`.** Every model judge so far was relative (could the cheap answer ship in place of the baseline's?), which is the wrong question when nobody trusts the baseline either, or when the thing under test isn't a model swap. `CriteriaJudge` (`rubrics/criteria.py`) reads a JSON checklist per feature (with a default, and a per-sample `meta.criteria` override), and a model judge answers YES or NO for each criterion. Score = fraction met; a criterion marked `critical` gates the score to 0.0; a criterion the judge gave no verdict on counts as missed, never met; a sample with no criteria is unscored. The judge sees the task and one answer, never the other arm's answer or any provenance. Because it's absolute, the **baseline is scored too**. Illustrative file: `Engineering/fixtures/criteria/sample-traffic-example-v1.json`. Mock runs use `MockCriteriaBackend` (deterministic, measures nothing). Named *criteria* rather than *rubric* because a rubric here is already the decision layer (`rubrics/spec.py`). Guide: `Engineering/Docs/GUIDE-Criteria-Judge.md`. 28 tests in `Engineering/tests/test_criteria_judge.py`.
- **`JudgeKey.absolute` and `JudgeKey.version`**, and `Judge.absolute`. Under a relative judge the control's true score is 1.0; under an absolute one it's the baseline's. `instar corpus calibration` now reads an absolute judge's control as *control minus baseline*, paired by sample (0.0 = the judge scored two same-model arms alike), and labels such judges `absolute` and `v=<criteria version>`. Keys written before these fields existed still load.
- **Human grading: `instar grade-sheet` and `instar rejudge --grades`.** Every model judge came with the advice to validate it against hand-graded examples, and there was nowhere to put hand grades. `grade-sheet` exports a saved arms transcript to a CSV a person fills in with a spreadsheet: one row per (prompt, candidate answer), the reference answer beside it, no arm names or models, rows shuffled by a seed. The grade column takes the LLM judges' own rungs (PASS / MARGINAL / FAIL), so human and model scores share a scale. `rejudge --grades sheet.csv --grader <id>` scores the run from the sheet through `HumanJudge` (`rubrics/human.py`); cost and latency replay unchanged, so the human's numbers sit beside every model judge's on the same answers, and `--corpus` stores them with judge family `human`. Item ids are hashed from content, so a sorted or filtered sheet still matches, identical pairs are graded once, and a sheet from another run is refused. A blank grade is unscored, never a pass. The grader id is recorded as the judge, so it must be a pseudonym (an id with `@` is refused). The sheet never overwrites an existing file without `--force`. Guide: `Engineering/Docs/GUIDE-Human-Grading.md`. 18 tests in `Engineering/tests/test_human_judge.py`.
- **`Judge.abstains()`**: a judge may decline to score a pair, which the runner then skips as unscored, the way it skips a failed call. Defaults to `False`, so existing judges are unchanged. `rejudge` warns with the count of pairs a judge abstained on.
- **Auditing the instrument: `instar corpus looks | rubric | labels`.** `rubric` is *rubric archaeology*: it applies a rubric to every candidate arm already stored in a corpus, without re-running anything, and reports per dimension and judge the verdict counts, how often the dimension was **binding** (at the worst level of a non-pass verdict), how often it was the **sole decider**, and the range its metric has taken. A dimension never binding under any judge has never changed an outcome and is a deletion candidate. `labels` is a *label-ceiling detector*: it flags samples where two or more different models give the same answer and the gold label disagrees (majority answer across repeats; a control arm is not a second opinion), and prints each model's agreement with gold. `looks` counts runs per workload and gold version, since every look at a fixed set spends some of it.
- **`arm.*` rubric metrics** (`arm.quality_mean`, `arm.quality_min`, `arm.quality_vs_control`, `arm.cost_saved_pct`, `arm.p50_ms`, `arm.p95_ms`, `arm.ms_per_output_token`, `arm.error_count`), so a rubric can judge an `instar arms` comparison, stored or fresh. `Rubric.evaluate_arm()` and `Rubric.evaluate_values()`; `binding_dimensions()` and `sole_deciders()` in `rubrics/spec.py`. An unknown cost is never scored as a saving. Example: `Engineering/fixtures/rubrics/arms-substitution-example-v1.json`.
- **`--split-role evolve|held_out|standard`** on `instar arms`, recorded in the corpus: what a workload is for, and so how its numbers may be used. A `standard` set is the yardstick and is never tuned against.
- `extract_label()` and `normalize_labels()` factored out of `LabelMatchJudge` so the label judge and the detector read labels the same way. 26 tests in `Engineering/tests/test_corpus_audit.py`.
- **`instar corpus` — read a measurement corpus across runs.** Four read-only subcommands over the directory `--corpus` writes: `runs` (each run with its judge, build and age), `calls` (filtered call records as JSONL, or `--count`), `calibration` (each judge's score on the same-model control, run by run: the judge's own error, and its drift once there are runs on more than one date), and `scores` (every judged arm against its run's control, with a verdict of better, worse, or **no measurable difference** when the gap is inside the noise band). All four share filters for tenant, workload, run kind, date range, judge family and model, feature and model, leave mock runs out unless `--include-mock`, show every row's age in days, and print JSON with `--json`. Standard errors are computed over samples rather than calls, so repeats of one prompt cannot make a band look narrower than it is, and arm-vs-control gaps are paired by sample. A model filter never drops the control an arm is read against. The band follows the noise-adjusted acceptance rule in Xia et al., *RRSI* (arXiv:2609.24972): a difference smaller than two runs of the same thing can differ by chance is not evidence. `core/corpus_read.py`; 24 tests in `Engineering/tests/test_corpus_read.py`.
- `Engineering/Docs/GUIDE-Measure-Your-Own-Prompts.md` — a task guide for an individual with no application or captured traffic: choose 10–30 of your own prompts (including a few your model got wrong), turn a folder of text files into a workload with a short script, and run one recipe (`instar arms` with your everyday model as the baseline, cheaper candidates, `--control`, a blind judge from another family, then a second-family `rejudge`). It covers what each corpus file contains and which are safe to share: `run.json` and `calls.jsonl` hold no prompt text, `transcript.json` holds all of it. Every command was checked end to end in mock mode.
- **A measurement corpus (`--corpus`) for `instar arms` and `instar rejudge`.** Each run is appended to `<corpus>/<tenant>/<YYYY>/<MM>/<run_id>/` as a `run.json`, one `calls.jsonl` record per (prompt, repeat, arm), and the transcript, and nothing in a corpus is ever rewritten. Several questions about the measuring itself can't be answered from one run, only from many runs stored with their context: is a judge drifting, is a gold label wrong, did a model improve or did its judge get kinder? `core/corpus.py` writes that context: the judge key, the control arm, the repeat index, when the record was made and by which build (version + git sha), and a tenant, consent flag, workload, task origin, rubric and gold versions, and the user's reaction when known. `rejudge --corpus` writes a new run whose records point at the original generations, so a second judge's scores sit next to the first instead of replacing them. `--tenant` is required with `--corpus`; `--upstream-consent` is off by default, and a sample can opt out of pooling but can't opt in on its tenant's behalf.
- **Every score now says which judge produced it.** `Judge.key()` returns a `JudgeKey` (kind, model, vendor family, blind), and `result.json` carries it. The same answers can score very differently under judges from different families, so a score without its judge isn't a measurement anyone can compare. `model_family()` guesses the family from the model id, returns `unknown` rather than a wrong guess, and can be overridden with `--judge-family`. Judges written without subclassing `Judge` are still recorded, by name.
- **Same-model control arms.** `Arm(is_control=True)`, or `--control` on the CLI, adds an arm serving the baseline's model. Its true quality is ~1.0, so what the judge takes off it is the judge's own error. A control arm must serve the baseline's model and can't be the baseline, and there can be only one. A judged run without a control now warns.
- `claude-sonnet-4-5` added to the built-in pricing table at $3/$15 per million tokens. The first live corpus run used it as a baseline and reported the direct arm's cost as `unavailable`, which left every cost delta against it blank. OpenRouter's provider-reported cost for the same model matched this rate.
- Transcripts record each entry's `repeat` and each arm's backend class and control role. Transcripts without these fields still load.

- **`instar arms` — an N-way comparison, and the first runner that lets each arm carry its own model.** `run_gateway` compares exactly two arms at one shared model, which cannot express the question most people actually have: *direct vs through a router at the same model vs through a router at a cheaper one*. The third arm only means anything if it varies the model. `core/arms.py` adds `Arm(name, backend, model)`, interleaves calls across every arm (same reasoning as the two-arm runner — blocked runs charge network drift to whichever arm went last), and reports latency percentiles **and cost** per arm, plus deltas against a chosen baseline. `run_gateway` is unchanged and still supported.
- **Provider-reported cost.** `CompletionResult.cost_usd` carries what the endpoint says a call actually cost, when it says so at all. `OpenAICompatBackend` now requests usage accounting (`usage: {include: true}`) and reads `usage.cost` — which is how a router reports the real charge, since only it knows which upstream host served the request and at what rate. Reported cost beats the pricing table, because a table cannot honestly cover 400+ models across 70+ hosts at prices that move weekly.
- **`cost_source` on every arm: `provider_reported` | `computed` | `unavailable`.** A run that mixes measured and estimated dollars is not comparing like with like, and a reader cannot tell that from the total alone — so the runner records the provenance and warns when arms disagree. An arm that is neither reported nor priced is `unavailable`, never `$0`: an unpriced model silently scoring zero is exactly how a cost report ends up flattering the cheapest-looking arm. A *partially* reported arm falls back to the table rather than summing real dollars with guessed ones.
- **`extra_body` on `OpenAICompatBackend`.** Endpoint-specific controls reach the wire without the harness growing a vendor-shaped API — OpenRouter's routing and privacy preferences go through as `{"provider": {"sort": "price", "zdr": true}}`. Keys the harness sets itself (`model`, `messages`, `max_tokens`) win, so a stray override cannot silently change what is being measured.
- **`instar arms --judge` — quality scoring across arms.** `run_arms` now retains the exact (repeat, sample) sequence every arm walked, so a `Judge` can line up call *i* across arms and score each non-baseline arm against the baseline on the same prompt. Without a judge the run warns in as many words: *a cheaper arm is not a better arm until its output has been scored*. An arm with no judge reports `quality_mean = None` — **unscored, which is never a pass** — rather than silently reading as fine. Pairs where either side errored are skipped instead of scored 0.0: a network failure is not a quality signal, and folding it in makes an unreliable arm look like a bad one, which needs a different fix.
- **`BlindPairwiseJudge` — a control on `LLMJudge`.** `LLMJudge` tells the judge outright which answer came from the premium model, which is a reason to prefer it that has nothing to do with the text; LLM judges also favour whichever candidate they read first. The blind variant strips provenance and shuffles position by a hash of the sample id (deterministic, so runs reproduce; uncorrelated with the arms). It is a control rather than a replacement: run both, and if they diverge you have learned something about your judge rather than about your models. Documented alongside the caveat blinding does *not* fix — a judge from the same model family as one of the arms may still favour its own house style.
- **Latency normalized by output tokens.** `ArmStats` records input/output token totals and `ms_per_output_token`. Raw wall-clock across arms is confounded on any generative workload — most of a call is spent emitting tokens, so an arm that happened to write shorter answers looks faster whether or not it is. When an arm's output length differs from the baseline's by more than a third, the run warns that the raw percentiles are not comparable and points at the normalized figure. Found by running a real three-arm comparison where the cheap arm produced 0.70x the tokens and looked 2.7 seconds faster.
- Model substitution is now surfaced as a finding: an arm that asked for one model and was served another records the served ids and warns. For a router that is the single most important thing a run can tell you.
- 41 tests in `Engineering/tests/test_arms.py` covering interleaving, per-arm models, the three cost states, partial-report fallback, substitution detection, output-length normalization, judge wiring (including the skip-on-error rule and unscored-is-not-a-pass), blind-judge determinism and label/position consistency, and the deliberate refusal to print a cost delta when either side's cost is unknown.
- `Engineering/Docs/COMPARISON-smevals.md` — where Instar sits relative to [smevals](https://github.com/prime-radiant-inc/smevals). smevals answers the capability question ("how good is model X at task Y?"); Instar answers the workload-economics question ("does this routing change pay off on my traffic?"). Documents the two-phase composition (candidate discovery in smevals, economic decision in Instar), an honest list of what smevals does better, and why cost tracking is an input-contract change rather than a feature. Three borrow items are named there and tracked for v0.2: a static HTML report, an `instar docs` command for coding agents, and an `--exec` runner backend.
- **The harness core.** Clean-room port of the internal gateway experiment code into `Engineering/src/instar/`, restructured to the package layout in `Planning/Project-Plan.md` §4:
  - `core/` — `TrafficSample` and JSONL workload fixtures; `FeatureCatalog`; cost math (per-token pricing, prompt-caching model, self-hosting break-even); the routing runner (`run_route`, `run_sweep`); the gateway A/B latency runner (`run_gateway`).
  - `providers/` — `Backend` interface and `CompletionResult`; `MockBackend` (deterministic), `AnthropicBackend` (optional SDK, lazily imported), and `OpenAICompatBackend`.
  - `policies/` — `AllStrongPolicy` (control), `FeatureCategoryPolicy` (rules baseline), `ClassifierPolicy` with a placeholder difficulty scorer and a documented seam for a trained router.
  - `rubrics/` — `LabelMatchJudge` (objective, gold-label), `LLMJudge` (PASS/MARGINAL/FAIL), `AutoJudge` (dispatches per sample), `MockJudge` (deterministic).
  - `reporters/` — `result.json`, Markdown report with per-call decision rows, and `sweep.csv` for charting.
  - `cli/` — `instar route` and `instar gateway`, both defaulting to hermetic mock mode.
- `OpenAICompatBackend` is implemented over `urllib` rather than an SDK, so vLLM, Ollama, LiteLLM, OpenRouter, and OpenAI are all reachable from a stdlib-only install.
- Synthetic, PII-free workload fixtures under `Engineering/fixtures/`: support triage (24 calls, gold labels, objectively scorable), marketing content ops (12, mixed), sales pipeline (10, including a prompt-caching refinement series), and a small mixed smoke sample. Example feature catalogs under `Engineering/fixtures/catalogs/`.
- 203 tests across 10 files, all hermetic. Includes a check that no private product terms leak into the shipped fixtures, enforcing the IP boundary in CI rather than in a reviewer's memory.
- `instar` console-script entry point and an `anthropic` optional-dependency extra.
- `Engineering/Docs/CODE-OVERVIEW.md` (architecture and extension points) and `Engineering/Docs/RUNBOOK.md` (task-oriented, including a walkthrough for measuring your own workload).
- `--strong-url` / `--weak-url` (with matching `--*-key-env`) on `instar route`, so either arm can be any OpenAI-compatible endpoint rather than Anthropic. This is what makes the CLI able to evaluate a self-hosted small model against a frontier baseline. The LLM judge runs on the strong arm.
- **Rubrics** (`instar.rubrics.spec`) — the framework for turning a measurement into a decision. A rubric is JSON: named dimensions, each binding a measured metric to a `pass_at` threshold and optional `marginal_at` band, agreed before the run and executed with `--rubric`. Two deliberate refusals: the overall verdict is the **worst** dimension rather than an average, so a large cost saving cannot cancel out a failing quality score; and a dimension the run could not measure returns `unmeasured`, which is never a pass. A failing verdict exits 1 so CI can refuse to publish a report its own rubric rejected. Closes the gap where `Planning/Engagement-Methodology.md` §B and `Marketing/Measuring-Your-AI-Costs.md` both promised per-dimension rubric scoring that the code did not implement.
- `Engineering/Docs/RUBRICS.md` (reference) and `Engineering/Docs/GUIDE-Creating-Rubrics.md` (a step-by-step guide to deriving dimensions and thresholds from a decision), plus an example rubric under `Engineering/fixtures/rubrics/`. The framework ships; the rubrics do not — per-department thresholds stay with whoever owns the outcome.
- `Engineering/Docs/GUIDE-Setting-the-Bar.md` — a one-page, jargon-free guide for the *decision owner* (not the operator): why the quality bar is a business judgment, how to set it, and the traps. Closes the audience gap where every other doc taught the person who runs Instar and nothing taught the person who signs off on the threshold.
- `Engineering/Docs/README.md` — a documentation index and reading map, so the docs are discoverable instead of scattered. A `00-README.md` symlink points to it so the index also floats to the top of a plain directory listing, while GitHub still renders the real `README.md` as the folder landing page. The index states the organizing principle: the docs are a **knowledge tree** with four teaching modes — Explain (reference), Guide (tutorial/task-guide), Do (lesson), Judge (case study) — and a new doc is placed by choosing its mode.
- `Engineering/Docs/LESSON-Rubrics-Hands-On.md` — a ten-minute, learn-by-doing lesson: run four commands in mock mode, change one threshold, watch the verdict flip from FAIL to PASS, then confront the trap of having moved the bar to match the result. Every quoted output is real and deterministic, so a learner sees exactly what the lesson shows.
- `Engineering/Docs/CASE-STUDY-Qwen-Triage.md` — a narrative case study built from the real Qwen 7B-vs-3B run: the rubric returned FAIL, and reading the two failing rows showed the labels were wrong, not the model. Teaches the judgment no tool automates — a verdict starts an investigation, it doesn't end one — plus the "faster to generate is not faster to respond" finding (1.8x throughput, 1.16x latency, because triage outputs are 2-3 tokens).
- `Engineering/Docs/PROVIDERS.md` — how to connect Instar to a hosted LLM (account, payment, key, base URL) and to a self-hosted SLM (Ollama/vLLM/llama.cpp, sizing, licensing posture), plus the small-model failure modes that look like poor quality but are really prompt or plumbing bugs.
- The route runner now records per-call latency and token counts, so cost arithmetic in a report can be audited rather than taken on faith, and rubrics can bind latency dimensions.
- Repository scaffolding: `Planning/`, `Engineering/`, `Marketing/`, `CLAUDE.md`, initial README stub.
- Governance files: `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` (Contributor Covenant v2.1), `SECURITY.md`, `CHANGELOG.md`.
- `pyproject.toml` with setuptools build backend, PEP 639 SPDX license fields, and configuration for `ruff` (lint + format), `mypy --strict`, and `pytest`. Package located at `Engineering/src/instar/` per `CLAUDE.md` §Organization principle.
- Smoke test at `Engineering/tests/test_smoke.py` — verifies the package installs and imports.
- SPDX license headers on all Python source files.
- CI baseline at `.github/workflows/ci.yml`: four parallel jobs — `ruff check` + `ruff format --check`, `mypy --strict`, `pytest -m 'not live'` on Python 3.11/3.12/3.13, and an SPDX-header check. Runs on push to `main` and on pull requests.
- `Planning/Engagement-Methodology.md` — first-draft spine for how Instar fits into a complete LLM evaluation engagement. Names eleven phases (A–K), annotates each with its IP-boundary side (OSS / mixed / private methodology), and frames the process as a loop rather than a line. Companion artifact (`Engineering/docs/How-Instar-Fits-an-Evaluation.md`) planned after the Week-2 code lift; Atelier playbook is a separate, private artifact.
- `Engineering/Introduction.md` — first-pass contributor-facing introduction, written for people Brian is inviting to the project.
- `Marketing/Measuring-Your-AI-Costs.md` — first-pass positioning + evaluation-process primer for leaders. Draft; not for publication until v0.1 gate clears (see `Planning/Naming.md`).

### Changed

- `result.json`'s `judge` object carries two more fields, `absolute` and `version`.
- `README.md` rewritten from mission stub to v0.1 shape: two-audience "Who it's for," status callout, install-from-source (PyPI deferred to v0.2), anti-scope, and pointers to `Planning/`. Subsequently corrected to document the CLI that actually exists (`instar route` / `instar gateway` over JSONL workloads) in place of an illustrative YAML interface that was never built.
- The feature-to-category map is now **user-supplied configuration** (`FeatureCatalog`, loaded from JSON) rather than a table baked into the source. An adopter measuring their own marketing or support workload declares their own features; the shipped catalogs are examples. Uncatalogued features default to foreground, so an omission costs money rather than quality, and the CLI names them on stderr.
- Gateway comparison arms are generic and user-specified (`--a-url` / `--b-url`), and calls are interleaved between arms rather than run in blocks, so drift in network or provider conditions cannot be attributed to whichever arm ran second.
- Reports carry their caveats inline — mock banner, failed-call count, unpriced-model warning, and small-sample warnings on tail latency percentiles — because these files get forwarded to people who never ran the tool.

### Removed

- The internal-gateway backend and the curated vendor feature-parity matrix from the source experiment. Both encoded private architecture and neither is runnable or useful outside it. Gateway comparison now measures latency only, on endpoints the user names.

### Deprecated

- *nothing yet*

### Fixed

- Bad input now exits with a message rather than a traceback: a malformed fixture line, an invalid catalog, a missing file, and an uninstalled provider SDK all report cleanly and exit 1.
- Reports stated that costs came from the placeholder pricing table "unless you supplied your own", which was misleading in both directions. A report now says which table it actually used, and the placeholder case is a prominent warning rather than a hedge in a footnote.
- The shipped support-triage fixture did not pin its output language. Against an exact-match scorer a multilingual model answering in another language scores 0%, which reads as a model-quality failure rather than the prompt bug it is.

- *nothing yet*
